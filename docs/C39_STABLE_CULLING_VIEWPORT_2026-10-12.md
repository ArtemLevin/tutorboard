# C3.9 — stable culling and wheel viewport continuity

Дата: 12.10.2026. Issue: [#201](https://github.com/ArtemLevin/tutorboard/issues/201).
Ветка: `fix/c39-stable-culling-viewport`.
Основание: `main` / `8a24b882b2a84472bc530691e47171a7775e74a6`.

## Решение и статус

Исправлены два воспроизводимых механизма: массовый remount при viewport
culling и потеря непрерывности wheel viewport между React commits.
Кандидат отделён от экспериментального стека PR #226–231; изменения Worker
и S7 listening suppression в него не перенесены.

**Correctness: локальные проверки пройдены. Performance GO: открыт.**
Слияние требует причинного сравнения и CI на точном SHA. Issue #201 остаётся
открытым; процент ускорения и достижение пользовательской цели пока не доказаны.

## 1. Почему пересоздавались группы

Раньше `BoardStage` формировал paint layers из видимых объектов, затем
`BoardSceneContent` строил непрерывные ink/non-ink runs. Ключ каждого run
содержал ID его первого видимого объекта. Выход этого объекта за границу
culling менял ключ родителя и пересоздавал всех оставшихся потомков.
Исчезновение промежуточного non-ink объекта также могло слить соседние runs.

Теперь paint layers и logical runs строятся по полному порядку `scene.items`.
Фильтрация видимости применяется внутри готового run с сохранением его ключа.
Порядок наложения и скрытые границы между ink/non-ink сохраняются.

Wrapper группы также стабилен при переходах 81 → 80 → 79 → 81 штрихов.
Порог 80 управляет регистрацией в cache coordinator. Изменение содержимого
или состава видимой группы освобождает её прежний scene/hit cache через
cleanup регистрации; устаревшая растровая копия повторно не используется.

Регрессионная проверка для 5k/10k: скрытие первого штриха вызывает **0**
повторных вызовов renderer для оставшихся объектов; сохранена идентичность
узлов. Возвращение первого штриха вызывает ровно один renderer. Исходный
механизм давал 4 999 / 9 999 вызовов в диагностическом React host probe.
Это причинное доказательство лишней работы, без перевода счётчиков в FPS.

## 2. Почему расходился viewport

Воспроизведены две гонки:

1. Debounce очищал wheel session, затем новый wheel до React render брал
   `previewViewport` из старого замыкания. В тесте zoom-in/zoom-out давали
   итог около 0,925926 вместо 1.
2. Эффект входящего `scene.viewport` воспринимал подтверждение собственного
   предыдущего commit как внешний сброс и отменял следующий wheel session.

Актуальный preview теперь синхронно хранится в ref. Новое событие использует
последний рассчитанный viewport даже между debounce и React render.
Собственные pan/wheel commits отмечаются в WeakSet и распознаются по ссылке
объекта: текущий reducer сохраняет `command.viewport` в документе.
Подтверждение обновляет authoritative ref, сохраняя начатый следующий жест.

Внешний viewport с отдельной идентичностью сохраняет прежнюю семантику сброса.
Совпадения чисел недостаточно для признания локального подтверждения.
Ownership потребляется один раз: последующее восстановление уже
подтверждённого объекта снова считается authoritative update.
При будущей сериализации/cloning на этом пути понадобится явный commit ID.

## 3. Измерительный протокол

Профиль проверяет 18 обработанных wheel inputs, чередование zoom 1,08 / 1,
финальный preview viewport и сохранённый viewport. Ошибка этих условий
останавливает тест до публикации успешного performance report.
К отчёту добавлены initial/final viewport, wheel zooms, SHA фактически
выбранного git HEAD и `worktreeDirty`. Сохраняются полные bounded JS/CDP traces,
включая случай последующего падения проверки камеры.

Static-heavy workflow теперь запускается и при изменениях canvas renderer
и core/board. Общий тип frame-trace используется обоими browser profiles;
дублирующая устаревшая декларация Window удалена.

## 5. Следующий проверяемый шаг

Контрольная версия с исправленным viewport и новым профилем:
`2110a8e03fe9adb836ffc1f470e35ff7be980323` — первый commit этой ветки.
Следующий commit добавляет стабильные группы. Это даёт корректную пару
для изоляции эффекта culling без переноса различий камеры в результат.

1. Собирать control и candidate в отдельных worktrees на одном runner,
   использовать одинаковые fixture, production build, browser и настройки.
2. Провести предусмотренные планом 3 цикла ABBA и независимый повтор,
   сравнивая полную траекторию, объекты, pixels/hit, active/commit latency
   и память. Сохранить raw traces обоих вариантов и их точные SHA.
3. Проверить gate: ≥20% парного выигрыша active p95 на 5k/10k, снижение
   доли >100 мс, отсутствие переноса задержки в commit и воспроизводимого
   ухудшения >10% на 3k/offscreen. Пройти cross-browser CI на candidate SHA.

Остаются ограничения: обход полного `scene.items`, переразбиение после
изменений документа, обход Konva descendants и scene/hit redraw. Фактическое
удаление первого объекта документа может изменить ключ run. Полностью
ушедший за экран run освобождается и создаётся заново при возвращении.
До шести логических paint layers могут сохранять пустые canvas при culling.
Пространственные chunks/tiles и постоянный ink cache требуют отдельного
измеренного решения после этого gate.
