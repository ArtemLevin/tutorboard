# TutorBoard — C3.9-S3: причинный анализ и план безопасной оптимизации

Дата: 10.10.2026. Репозиторий: [ArtemLevin/tutorboard](https://github.com/ArtemLevin/tutorboard). Задача: [#201](https://github.com/ArtemLevin/tutorboard/issues/201).

**Рекомендация:** следующий законченный блок — устранение повторной инвалидации неизменного содержимого при сохранении viewport. Первый кандидат: сохранить ссылку на `scene.items` при изменении только viewport/метаданных документа. Перед включением выполнить отдельное браузерное A/B и исправить атрибуцию измерений. Пространственная отрисовка и тайлы остаются следующим экспериментом при подтверждённом преобладании scene/hit redraw.

**Статус этого документа:** анализ текущего кода, проверка первичных CI-логов, локальные проверки механизмов и подробный план реализации. Новая production-оптимизация здесь не внедрена; ускорение браузера новым кандидатом ещё не измерено. На момент завершения анализа удалённые ветки, PR и Issue не изменялись; рабочая копия `main` была чистой. Позднее этот отчёт включён в документацию вместе с обновлением `PLAN.md`; production-код при обновлении плана не менялся.

## 3. Существенные ограничения нынешнего измерителя

### 3.1. Active-интервал содержит промежуточные сохранения viewport

В `summarizePhases()` active определяется как rAF-интервалы, заканчивающиеся между первым и последним wheel-событием. Сохранение viewport запускается после 120 мс без нового wheel. Следующее событие тест отправляет после ожидания кадра, поэтому тяжёлая отрисовка увеличивает расстояние между событиями.

Пересчёт `inputTimesMs` из исходных логов:

| Сцена | Промежутки между wheel >120 мс в повторах 1 / 2 / 3 |
| --- | --- |
| 3k, плотная | 17/17 · 17/17 · 17/17 |
| 5k, плотная | 17/17 · 17/17 · 17/17 |
| 10k, плотная | 17/17 · 17/17 · 17/17 |
| 10k, offscreen | 0/17 · 0/17 · 9/17 |

Само превышение 120 мс ещё не доказывает исполнение каждого таймера: очередь main thread тоже влияет. Однако в логах есть прямое совпадение промежуточного `wheel-viewport-persist` с active-кадром: плотные 10k, повтор 2, rAF gap **516,6 мс**, persist около **518 мс**. В третьем offscreen-повторе active-кадры 183–250 мс также совпадают с persist длительностью около 231–265 мс.

Таким образом, active p95 — полезная сквозная метрика данного драйвера, но она смешивает визуальные обновления и промежуточные сохранения. Замедление рисования способно вызвать больше сохранений, которые дополнительно задерживают следующий кадр. Это правдоподобная петля усиления задержек, требующая проверки session-by-session.

**Исправление измерений:** сохранить историческую метрику и дополнительно размечать каждый wheel-session, каждое сохранение и каждый пересекающий границу кадр. Отдельно считать кадры без persist, кадры с persist, финальное сохранение и settling. Кадры со смешанной работой должны оставаться в общей метрике.

### 3.2. `board-commit` не является чистым временем React

Метка ставится в wheel-handler перед `setPreviewViewport`, завершается в layout effect. Время включает ожидание планировщика, React, синхронный React-Konva commit и возможную работу между ними. Измеритель хранит только один pending timestamp. `react-ink-run` сообщает факт commit группы и число элементов, его duration всегда нулевой.

Например, в плотных 10k зарегистрированы `board-commit` до примерно 868 мс, Konva scene до 111 мс и hit до 98 мс в отдельных медленных окнах. Это наблюдения разных событий. Их нельзя складывать в проценты общего времени или объявлять 868 мс «стоимостью React».

Нужны отдельные bounded-маркеры selector/bounds/query/run construction/transform binding и диагностическая React profiling сборка. Производительность итогового кандидата измеряется обычной production-сборкой с трассировкой выключенной.

### 3.3. Сохраняется только часть исходной трассы

Скачанный artifact static-heavy содержит четыре файла: `repeat-1.log`, `repeat-2.log`, `repeat-3.log`, `summary.json`. Логи включают метрики, все rAF gaps и ограниченные события пяти самых медленных окон. Полные массивы всех JS/CDP events в этом архиве отсутствуют.

В текущем тесте JSON report прикрепляется через `testInfo.attach`; сам report содержит сокращённую атрибуцию. Для нового анализа следует явно писать полные обезличенные bounded traces в уникальную папку каждого повторения и архивировать её. Нужны счётчики потерянных событий для всех рекордеров: rAF сейчас ограничен 300 timestamps, JS — 12 000 событий; у CDP есть лимит 20 000 и dropped count. Переполненный опыт исключать из выводов о причинности.

### 3.4. Следует проверять фактическую нагрузку

Сейчас проверяются число объектов, кодеки, DPR, topology и количество входных событий. Для более сильного gate добавить:

- Хэш всего синтетического документа и реальных байтов изображений, seed и порядок объектов.
- Реальный размер области доски, последовательность offset/zoom, число обработанных входов, финальный viewport и число сохранений. Одинаковых вызовов `mouse.wheel()` недостаточно для доказательства одинакового выполненного пути.
- Готовность декодирования всех десяти изображений по диагностике renderer; ожидание 24 кадров само по себе не удостоверяет это состояние.
- Отдельное описание холодности pen-cache, decode-cache и HTTP/asset cache.
- Идентичность документов и входов между A/B без требования одинакового числа rAF-кадров: ускорение само меняет это число.

## 4. Причинная цепочка по текущему коду

| Участок | Что происходит | Степень подтверждения |
| --- | --- | --- |
| Wheel → `previewViewport` | Изменяется React state; 120-мс таймер коммитит viewport | Код и browser trace |
| Visibility query | По каждому preview проходят заранее вычисленные bounds всех видимых по флагу объектов документа | Код; локальная проверка |
| Стабильный состав видимых элементов | Visibility index возвращает прежний массив; pen-only runs получают постоянный `zoom=1` | Код и существующие тесты |
| Изменение состава на краю viewport | Меняются visible array, batches и run-объекты; большие ink runs снова проходят React mapping/reconciliation | Код; в медленных окнах есть commits ink-runs, но доля CPU отдельно не измерена |
| Родительский Konva transform | Меняются scale/offset; сбрасываются производные transform-кэши потомков; запрашивается layer redraw | Установленная Konva 10.3.0, локальный структурный эксперимент |
| Canvas redraw | Статический content layer рисует scene и hit; без готового кэша обходит дочернюю геометрию | Код Konva и browser markers |
| Transformer effect | Каждый preview запускает поиск `.board-transform-target` по сцене, включая пустое выделение | Прямо подтверждено кодом |
| Persist | Остаётся одна полная проверка текущего BoardDocument; новый document сохраняет ссылки на содержимое | Код reducer и тесты C3.9-D; browser trace показывает большие persist интервалы |
| Scene selector после persist | Создаёт новый массив `items` и Map даже при прежних объектах; индекс bounds и run-структуры перестраиваются | Подтверждено кодом и отдельной локальной проверкой |
| Compositor | Chromium обновляет слои и композитит результат canvas | Есть совпадающие события, окончательная причинная доля неизвестна |

### Уже работающие оптимизации

`createBoardVisibilityIndex()` рассчитывает геометрию при создании индекса и сохраняет предыдущий результат при неизменных membership/order. `BoardSceneRun` и `BoardRenderItemView` мемоизированы; неизменным pen-объектам передаётся `zoom=1`.

Поэтому утверждение «каждый wheel заново строит Path всех штрихов» слишком широкое. Повторная работа зависит от сохранения документа, изменения видимости, ссылок на props и операций Konva ниже React.

Статическая сцена уже использует **один committed content layer**. Уменьшение числа GIF-слоёв не решает основной случай с PNG/JPEG. Лимит шести committed layers сохраняется.

Разбиение массива на batches по 250 элементов тоже не является независимой пространственной отрисовкой: `groupInkRenderRuns()` снова объединяет соседние pen-элементы в непрерывный ink run, потенциально на тысячи объектов.

### Локальная проверка на текущем main

Node `24.19.0`, npm `11.9.0`, Vitest/jsdom. По 2 прогрева и 7 замеров. Геометрия — varied fixture, десять стандартных 1×1 PNG. Это CPU-проверка механизма; большие PNG/JPEG, canvas и compositor в неё не входят.

| Всего штрихов / задано видимых | Selector, медиана | Перестроение bounds, медиана | Запрос сохранённого индекса, медиана |
| --- | ---: | ---: | ---: |
| 3k / 2,4k | 0,66 мс | 2,33 мс | 0,080 мс |
| 5k / 4k | 1,38 мс | 2,18 мс | 0,071 мс |
| 10k / 8k | 2,72 мс | 5,81 мс | 0,105 мс |
| 10k / 1k | 2,48 мс | 4,21 мс | 0,060 мс |

Во всех случаях viewport-only обновление создавало новый `items`, сохраняя каждый отдельный `BoardRenderItem`. Повторное использование исходного visibility index давало тот же состав и порядок; при выбранных малых движениях сохранялась и ссылка результата.

Эти измерения подтверждают устранимую работу, но сами по себе объясняют только единицы миллисекунд на данной машине. Возможный каскадный выигрыш от сохранения React/Konva структуры нужно измерить в браузере.

Дополнительная проверка использовала реальные Konva Groups без рисования: три узла на модельный объект, геометрия представлена пустой leaf-group. Для 8 000 объектов изменение parent transform вызвало **24 001** проход базового сброса кэша; поиск transform-target посетил **24 000** потомков. Это доказательство механизма обхода. Числа узлов и CPU-время реальной доски будут другими, поскольку один штрих может иметь несколько Path и внешние transforms.

### Границы причинного вывода

Подтверждены лишняя инвалидация сцены при viewport-only, безусловный поиск transformer-узлов и обход дерева Konva при изменении parent transform. Подтверждены реальные длинные scene/hit/persist интервалы.

**Единственный доминирующий источник всех задержек пока не установлен.** Имеющиеся события показывают несколько путей, вклад которых меняется между повторами. Без новых управляемых A/B нельзя обещать, что сохранение `scene.items`, transformer guard или тайлы обеспечат нужный p95.

## 5. Следующий законченный блок: C3.9-S3

Рабочее название: **«Стабильная статическая сцена при изменении viewport»**.

Единица завершения: один локальный production-кандидат, доказательство причины и выигрыша на одинаковой нагрузке, регрессионный gate, полный CI и отчёт. Исследовательские варианты остаются отдельными экспериментами. Новую ветку создавать от проверенного `main`; PR #216 в основу блока не включать.

### Шаг 1. Сделать результат проверяемым

Файлы: `tests/e2e/c39-large-board-profile.spec.ts`, `tests/e2e/c39-frame-attribution.ts`, `src/adapters/canvas-konva/board-frame-trace.ts`, новый parser/тесты под `scripts/c39` и `tests/node`.

1. Присвоить каждому принятому wheel отдельный input ID внутри session ID. Записать полученный delta, resulting viewport, время до/после cache begin, dispatch, layout, persist start/end, cancel.
2. Добавить длительности `scene-select`, `visibility-index-build`, `visibility-query`, `paint-run-build`, `transformer-bind` и счётчики новых/переиспользованных items/runs. Записывать только числа, типы и синтетические идентификаторы.
3. Измерять React subtree commits/actualDuration в отдельной profiling сборке, отдельно — Konva host commit и реальный scene/hit draw. Сверить включённую/выключенную диагностику на той же версии.
4. На slow-frame отчёте показывать перекрывающиеся интервалы и критический поток. Exclusive CPU считать только там, где он измерен; вложенные/межпоточные интервалы не суммировать.
5. Выделить промежуточные persist и mixed-phase frames. Сохранить исходный active p95 для сопоставимости.
6. Явно сохранять raw JS/CDP/rAF, manifest, summaries и скриншоты каждого run. У любого буфера — cap, dropped count и teardown.

**Выход:** можно объяснить каждый выбранный медленный кадр либо явно обозначить неизмеренный участок; сохранений между wheel больше не прячет название active.

### Шаг 2. Провести независимые причинные вмешательства

| Вариант | Единственное изменение | Проверяемый вывод |
| --- | --- | --- |
| A0 | Текущий main | Общая база |
| A1 — основной кандидат | Сохранить `scene.items` при viewport-only/метаданных | Убирает ли потеря ссылок значимую часть index/run/React работы и задержки кадров |
| A2 — отдельный эксперимент | Пропустить поиск transform-target при пустом допустимом выделении; очистить прежние nodes при переходе в пустое состояние | Значим ли полный поиск узлов в текущем профиле |
| A3 — только при необходимости | Стабильные векторные пространственные фрагменты внутри исходных ink-runs | Снижает ли локализация membership churn React-работу при пересечении края viewport |
| A4 — только после подтверждения raster-доминирования | Ограниченное тайловое представление scene и корректного hit-слоя | Снижает ли сокращение redraw scene/hit сквозные задержки с учётом подготовки и памяти |

Сначала сравнить A0/A1. A2 проверять отдельно, чтобы не приписывать его эффект A1. A3/A4 не должны попадать в тот же production diff без собственного причинного результата.

Разделение scene и hit измерять настоящими вызовами обоих путей. Отключение hit-testing или подмена canvas пустым содержимым меняет задачу и не может служить доказательством безопасного ускорения. DPR1/DPR2, trace on/off и профиль renderer/raster threads использовать как диагностические факторы, явно отделяя их от production A/B.

### Шаг 3. Реализовать минимальный A1 после подтверждения

Основной production-файл: `src/core/board/selectors.ts`.

- Сохранить нынешние сигнатуры `BoardSceneSelector`, `BoardSceneReadModel`, `reset()` и `cacheSize()`.
- Для того же документа по ID при неизменных ссылках `objects`, `order`, `groups`, `geometryImports` вернуть новый scene wrapper с актуальным viewport и **прежним `items`**. Эти поля покрывают зависимости renderer read model текущей версии.
- Обновить сохранённый `previousDocument`; прежний cache оставить ограниченным текущей сценой. При изменении содержимого использовать существующий путь формирования items.
- При `reset`, смене документа и изменениях состава сбрасывать/обновлять кэш согласно нынешней модели. Не вводить глобальный Map по всем доскам.
- Не использовать глубокое сравнение всего документа на каждом wheel. Не считать визуальное переиспользование доказательством валидности документа.
- В reducer сохранить обязательную полную входную валидацию, строгие schemas viewport/timestamps и действующее undo/redo.
- В `BoardStage` проверить, что удержание `scene.items` действительно сохраняет index и run references. Отдельно проверить cache end/cancel, очистку, удаление медиа и prewarm effect, который зависит от `scene.viewport`.

Предлагаемый fast path опирается на уже используемую в selector модель неизменяемых объектов. Он не расширяет границу доверия к импортируемым данным. Новое поле «версия сцены» в persisted format не требуется.

**Ожидаемый эффект:** viewport-only commit больше не означает полную перестройку render read model. Полная валидация документа и реальный canvas redraw останутся измеряемыми остаточными затратами.

### Шаг 4. Если A1 не улучшает пользовательские задержки

Зафиксировать отрицательный результат и не представлять уменьшение счётчиков как ускорение доски. Не наращивать A1 случайными оптимизациями для получения зелёного отчёта.

По результатам атрибуции выбрать следующий отдельный блок:

- React membership churn → стабильные фрагменты pen-run с ограниченной локальной пересборкой.
- Konva scene/hit → прототип ограниченных тайлов.
- Persist/валидация → отдельное исследование жизненного цикла viewport-команд с сохранением trust boundary; изменение валидации не включать автоматически в S3.
- Compositor/raster → эксперимент с объёмом инвалидируемой поверхности при том же документе, качестве и DPR.

## 6. Требования к пространственному прототипу

Это отдельная условная ветвь плана; она описывает достаточные условия безопасного эксперимента.

1. Делить **каждый непрерывный ink-run в исходном z-order**. Изображение, текст или другой объект между штрихами остаётся барьером. Перенос всей рукописи в один верхний слой меняет порядок перекрытий.
2. Для одного run пространственные участки имеют неперекрывающуюся внутреннюю область композиции. Штрихи, пересекающие границы, рисуются с полным геометрическим покрытием и padding, затем обрезаются при композиции. Двойное смешивание прозрачных краёв недопустимо.
3. Применять точечную инвалидацию по объединению старых и новых bounds при рисовании, частичном стирании, изменении стиля, перемещении, групповых transforms, undo/redo и remote updates.
4. Сохранить точную геометрию и оригинальные объекты документа. Растр — производное представление с безопасным возвратом к vector path.
5. Hit canvas должен соответствовать актуальному viewport, membership и z-order. Нельзя держать устаревшую карту попаданий во время wheel, первого клика, erase или нового pen-input. Каждый исходный object ID остаётся адресуемым.
6. Подготовка — ограниченными порциями вне input-handler. `requestIdleCallback` с остатком 8 мс не гарантирует, что монолитная операция `cache()` уложится в 8 мс. Нужно ограничивать сам объём работ и проверять задержку pen-input во время подготовки.
7. Задать бюджет до создания bitmap: scene + hit + временные поверхности, физические пиксели с DPR, число активных участков и предел размера одного canvas. Для первой попытки не расширять существующий дополнительный scene-cache бюджет 4 млн физических пикселей; hit и temporary учитывать отдельно в общей верхней оценке. Формула RGBA — минимум `width × height × 4` байт на поверхность, без учёта копий/служебной памяти.
8. При исчерпании бюджета, отмене подготовки, смене zoom-bucket, resize, смене доски или unmount — корректный fallback и освобождение. Запрет на монотонное накопление старых тайлов/ссылок.
9. Новые полноэкранные Konva Layers не добавлять ради каждого участка. Сохранить существующий предел committed layers. Бюджет tile-cache учитывать совместно с WheelInkCache, исключая удвоение кэшей.
10. Проверить чёткость, alpha, seams и hit во время жеста, сразу после commit/cancel и при DPR1/2. Постоянное снижение качества ради FPS в этот блок не входит.

## 8. Протокол A/B и критерии решения

### Одинаковая нагрузка

Основная матрица — те же 3k/5k/10k, соответственно 2,4k/4k/8k заданных видимых, плюс offscreen 10k/1k. Во всех случаях 4 PNG + 6 JPEG по 1536×1536, одинаковые реальные байты, порядок и геометрия, DPR2. Отдельные проверки DPR1 и prewarmed/cold состояния; короткий GIF regression сохраняется.

Большие документы создавать через тестовое наполнение IndexedDB и штатное восстановление. Импорт >10 MiB должен продолжать предсказуемо отклоняться публичным интерфейсом.

### Порядок и повторяемость

- Использовать production builds baseline/candidate с одними зафиксированными браузером, viewport и runner image. Записывать ОС, CPU, browser flags, GPU renderer/backend и доступность compositor-данных.
- Для каждого сценария выполнить 3 цикла ABBA: по 6 запусков каждой версии. Внутри каждого блока новые browser contexts, сопоставимое исходное состояние. Добавить независимый запуск процесса/CI-job для оценки межзапусковой вариабельности.
- Не запускать одновременно другие нагрузки на той же машине. Trace-on диагностику и trace-off итоговую оценку разделить.
- Сначала воспроизвести существующий 18-input профиль. Затем добавить заранее заданный профиль входов, расписание которого не зависит от ожидания отрисовки. Записывать как отправку, так и фактическую доставку; сохранять данные о coalescing и main-thread задержках. Скриптовая отправка синтетического WheelEvent не заменяет проверку штатного ввода браузера.
- Контролировать одинаковую результирующую траекторию viewport. Любое несовпадение, потерю входов или объектов расследовать до принятия более быстрого результата.
- Не подбирать продолжительность под понравившийся p95. Число запусков и верхний лимит исследования фиксировать заранее. Недостаточные/противоречивые данные дают статус INCONCLUSIVE.

### Метрики

Публиковать по каждому повтору: p50/p95/p99/max rAF gaps, счётчики >25/>50/>100 мс, длину измерительного окна, input count, final viewport, число sessions/persist, pen input-to-paint, Long Tasks, selector/query/build/transformer durations, React commits, Konva scene/hit, raster/decode state, resource/memory counters.

Отдельные срезы: first-input, active без persist, active с persist, финальный commit, settling. Сквозной active не заменять отфильтрованным. React duration и GPU/CPU время публиковать с их точным смыслом; недоступную GPU-метрику обозначать `unavailable`.

Для парных выводов считать дельты по независимым запускам/ABBA-блокам и интервал неопределённости. Bootstrap по кадрам одного запуска создаёт ложную уверенность; предпочтителен resampling блоков. При шести парах интервалы остаются грубыми. Для выводов о p99 желательно не менее 1000 active-интервалов на вариант и несколько независимых запусков; даже это не заменяет анализа хвоста.

### Предлагаемый gate блока S3

Это заранее предлагаемые критерии для следующего кандидата, а не достигнутый результат:

1. На 5k и 10k медианный парный выигрыш сквозного active p95 не менее **20%**, с одинаковым направлением в независимом повторе. Доля >100 мс снижается; улучшение не объясняется другой траекторией, пропуском событий или переносом работы в commit.
2. На 3k и offscreen нет воспроизводимого ухудшения p95 более 10% за пределами установленного шума. Сравнивать также wall time и rate медленных кадров.
3. Commit p95, first-input, pen input-to-paint и память не получают воспроизводимой регрессии. Pen p95 проверяется по прежней цели ≤16,7 мс; если baseline её уже нарушает, это отдельно фиксируется как открытая проблема, без объявления полной готовности.
4. Все pixel/hit/data проверки пройдены. Для A1 ожидается точное совпадение стабильных статических снимков в одном браузере; любой допуск должен быть обоснован до сравнения, а различия локализованы.
5. CI, cross-browser smoke, профильный benchmark и lifecycle checks успешны на точном candidate SHA.

Если A1 даёт небольшой выигрыш только в CPU-счётчиках, критерий production-оптимизации большой доски не выполнен. Можно сохранить результаты исследования, продолжив выбор причины. При подтверждённом частичном ускорении Issue #201 всё равно остаётся открытым до достижения общего пользовательского качества.

Общая цель из #201 — p95 около 33,3 мс, max <100 мс на согласованной тяжёлой сцене и полноценные C3.9-E/F проверки. Мердж отдельного доказанно полезного блока и закрытие всей проблемы — разные решения.
